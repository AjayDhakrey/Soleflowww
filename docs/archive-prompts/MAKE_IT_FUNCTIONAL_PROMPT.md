========================================================================
PART 0 — VERIFIED ROOT CAUSES (fix all of these)
========================================================================
1. context/AppContext.tsx → recordPayment() writes directly with supabaseApi.insertPayment() and supabaseApi.updateCustomer(). RLS (supabase/migrations/0007_rls.sql) limits these direct writes (payments/customers writes only allowed for admins or the client's own salesman), and failures are only console.warn'd — the UI updates local state and shows a success toast anyway. After any reload/refetch the change is gone.
2. recordPayment() silently uses FAKE fallbacks: customers[0], amountDueBefore 230000, paymentAmount 100000, orderId 'ORD-0148', paymentDate 'Today, 24 Oct 2024', utrRef 'UPI/428901239841', receipt number `SF-REC-${403 + payments.length}`.
3. components/payments/RecordPaymentModal.tsx defaults to customers[0], uses beforeDue fallback 230000, and caps the default amount at ₹1,00,000 (Math.min(amountDue, 100000)).
4. services/payments.ts calls supabase.rpc('record_payment', { p_payment, p_allocations }) but the SQL function in 0005_rpc.sql takes (p_client_id, p_order_id, p_amount, p_method, p_reference, p_allocations, p_notes, p_receipt_path) → the call can never succeed. It is also not used by any screen.
5. Two data layers: every page reads arrays from useApp() (AppContext), while services/* and hooks/* (useClients, useOrders, usePayments, useDesigns, useCustomerMetrics, react-query) exist but no page uses them. Data gets out of sync.
6. auth/AuthProvider.tsx falls back to a MOCK user when Supabase login fails, and AppContext has its own MOCK_USERS login. Without a real Supabase session, auth.uid() is null and every RPC/RLS write fails.
7. pages/sales/CollectionsPage.tsx filters "my" customers with `salespersonName.includes(currentUser.name)` (fragile) and shows hard-coded KPIs "₹8.40L" (Collected This Month) and "₹1.50L" (cheques in transit).
8. Hard-coded KPI values elsewhere: PaymentsPage "₹4.20L", "₹0.80L", "₹21.40L"; ReportsPage "₹48.60L"; VisitsPage "₹3.80L".
9. Buttons that only call showToast (no real action): AuditLogPage export CSV + audit details; ManufacturersPage "Actions for…"; OrdersPage "Actions for…"; PaymentsPage "aging balance sheet exported as PDF"; ReportsPage "Generated GST Wholesale Audit Ledger"; FollowUpsPage "New follow-up reminder scheduled"; SalesTeamPage export route manifest + "Calling…"; VisitsPage "Visit details saved". There are ~50 showToast calls in total — audit each one.

========================================================================
PART 1 — NON-NEGOTIABLE RULES FOR EVERY ACTION IN THE APP
========================================================================
- ONE source of truth: Supabase → services/* → react-query hooks. AppContext keeps its current function names/props so existing components keep working, but its data arrays come from the react-query cache and its mutation functions call the services. No component keeps its own copy of server data.
- Every write goes through a permission-checked RPC (SECURITY DEFINER, SET search_path = public) — never direct table writes from the browser for money, status, balances or ownership.
- Every mutation: await the server → on success update/invalidate the affected queries → then show the success toast. On failure: show the database's readable error, roll back any optimistic change, keep the form open with the user's input.
- Submit buttons show a spinner and are disabled while saving (no double submits). Send an idempotency key with payment submissions.
- No fake fallback values anywhere. Missing required data = validation error, not a made-up number.
- IDs, receipt numbers and dates are generated by the database. Dates stored as timestamptz and displayed in Asia/Kolkata.
- Supabase Realtime on customers, payments, orders, order_items, follow_ups, field_visits, notifications, discount_requests → invalidate the related queries, so the admin sees a salesman's collection within seconds without refreshing.
- Salesman data scope comes from RLS / salesman_id, not name matching.

========================================================================

- Remove the parallel MOCK_USERS login path from AppContext in production (keep it only for demo mode). currentUser comes from AuthProvider's profile (id, role, salesman_id).
- Demo mode: show a small "Demo mode — changes are not saved" badge in the header, and make all mutations update the local demo state consistently so demo still behaves correctly.
- Document in README how to create the admin and salesman accounts (Supabase Auth user + profiles row with role and sales_team_id).
